# Android platform review — Sabeel (com.sabeel.steps)

**Reviewer:** android-platform (independent, adversarial) · **Date:** 2026-11-17 · **Artifact:** `app/src/main` matching debug APK sha256 `324690…B9E` (APK not rebuilt; no release build existed) · **Method:** static source review + merged-manifest check; **no Gradle, no device**.
**Verdict:** **not ship-ready.** One Android 14+ crash defect (F1) is reachable from the app's own permission-skip flow, and the step counter can stop permanently with no user-visible signal (F2). The privacy posture and FGS declaration mechanics are genuinely good, but the runtime claims in README are unverified and, in the crash path, false.

## 1. SCOPE & METHOD

Read every line of `AndroidManifest.xml`, `service/StepCounterService.kt`, `service/WalkTrackingService.kt` (621 lines), `service/WalkTracker.kt`, `platform/{Permissions,Notifications,Reminders,BootReceiver}.kt`, `MainActivity.kt`, `SabeelApp.kt`, `AppContainer.kt`, the root scaffold/insets/theme files and the call sites that start services (`AppViewModels.kt`, screens); checked the **merged debug manifest**, the 41-test surface and `docs/legal/evidence/` runtime artifacts. Each rule was checked against current official Android 14/15/16 documentation and the API 26–36 behavior matrix; findings state the version where a rule applies. Labels: **[evidence]** = read in source/APK/manifest; **[inference]** = deduced from platform docs but not executed on a device. I did not modify app source, tests, build files or README.

## 2. VERIFIED STRENGTHS

- **No network surface [evidence]:** merged debug manifest contains no `INTERNET`/`ACCESS_NETWORK_STATE` (main manifest lines 15–17 actively `tools:node="remove"` them; merged manifest re-confirmed); no ad/analytics/Firebase dependency. Offline claim holds statically.
- **Backup extraction blocked [evidence]:** `android:allowBackup="false"` plus `dataExtractionRules`/`fullBackupContent` excluding all domains and device transfer (AndroidManifest.xml:21–23; `res/xml/data_extraction_rules.xml`, `backup_rules.xml`).
- **Correct Android 14 FGS declaration mechanics [evidence]:** both services declare types and the matching normal permissions — `health` + `FOREGROUND_SERVICE_HEALTH` (manifest:10,41–44), `location|health` + `FOREGROUND_SERVICE_LOCATION` (manifest:11,47–50); `FOREGROUND_SERVICE` present (9). This is the part most apps get wrong; it is present.
- **startForeground timing [evidence]:** called in `onCreate` before any slow work (StepCounterService.kt:73–109→212–221; WalkTrackingService.kt:91–99→394–408), so the 5-second rule is met (all API levels), and the notification channel is created first (StepCounterService.kt:74–77; Notifications.kt:43–79).
- **Type gating by OS level [evidence]:** type = 0 below API 30, `HEALTH` on 30+, `LOCATION` when location permission exists (StepCounterService.kt:212–219; WalkTrackingService.kt:394–404). No `startForeground` type misuse on old APIs.
- **PendingIntent hygiene [evidence]:** every PendingIntent is `FLAG_IMMUTABLE or FLAG_UPDATE_CURRENT` (Notifications.kt:172–177; WalkTrackingService.kt:434–442); the stop action correctly uses `getForegroundService` (API 26+ requirement), and a user tapping a notification is a documented background-start exemption, so the stop action works even when the app is backgrounded.
- **Restart design [evidence]:** `START_STICKY` with null-intent handling (StepCounterService.kt:111–119; WalkTrackingService.kt:101–122), boot start wrapped in `runCatching` (BootReceiver.kt:31–34), boot work delivered through `goAsync()` + finally-finish (BootReceiver.kt:24–43).
- **Boot FGS is legal on the health type [evidence/inference]:** BOOT_COMPLETED is an explicit BFSL exemption, and Android 15's restricted boot types are dataSync/camera/mediaPlayback/phoneCall/mediaProjection/microphone — health and location are still allowed. The code's boot start is therefore structurally correct **provided** F1's prerequisite is met.
- **Scheduling restraint [evidence]:** WorkManager only; no exact alarms, no wakelocks (Reminders.kt:22–23; grep over `app/src/main`); periodic 15 min is the platform minimum and uses `KEEP` (Reminders.kt:49–57); reminder uses unique `REPLACE` work (32–42).
- **Location lifecycle [evidence]:** provider registration only inside `beginWalk` (WalkTrackingService.kt:126–174,258–280) and unregistered on stop/destroy (176–242,555–564); no location access while not walking; no `ACCESS_BACKGROUND_LOCATION` requested — correct for a type-`location` FGS started from a visible activity.
- **Android 16 / large-screen posture [evidence]:** edge-to-edge via `enableEdgeToEdge()` (MainActivity.kt:25–27) with `Scaffold(contentWindowInsets = WindowInsets.safeDrawing)` (SabeelRoot.kt:95), no orientation lock, no resizability opt-out, 16 KB-aligned bundled `.so` files (evidence EV-08) → no known API 35/36 layout or page-size breakage.
- **Step pipeline is reboot/midnight-aware in principle [evidence]:** cumulative-`TYPE_STEP_COUNTER` raw baseline with rebase on decrease and midnight zeroing (StepPipeline.kt, exercised by StepPipelineTest) — the correct approach for the sensor.

### 3.2 Critical / High detail

**F1 — Android 14+ crash from the app's own "skip permissions" flow.** The Android 14+ contract for `android:foregroundServiceType="health"` is: at `startForeground()` time, at least one of — `HIGH_SAMPLING_RATE_SENSORS` declared, or a granted `BODY_SENSORS`/`READ_HEART_RATE`/`READ_SKIN_TEMPERATURE`/`READ_OXYGEN_SATURATION`/`ACTIVITY_RECOGNITION` — must hold, otherwise the system throws `SecurityException` after the call and "might cause your app to crash" (fgs-types-required docs). Sabeel declares only `ACTIVITY_RECOGNITION` as the qualifying prerequisite (manifest:7,10), so the service is legal **only while that runtime permission is granted**. `OnboardingViewModel.finish` starts the service regardless (AppViewModels.kt:295–305 after `OnboardingScreen.kt:164–170`, whose Finish button is never disabled), so the first thing a permission-skipping user gets on Android 14/15/16 is a process crash — not a degraded step count. The same prerequisite hole exists in the boot path (BootReceiver.kt:31–34) and in the walk service's step-only `HEALTH` fallback (WalkTrackingService.kt:394–404) when both location and activity recognition are denied. Because the throw happens on the service main thread, the caller's `runCatching` cannot save it; the fix must be a gate *inside* the service (or, better, only start after a grant) plus a UI state that explains it.

**F2 — the service does not come back, and the retry is illegal.** Only three call sites start `StepCounterService`: onboarding completion (AppViewModels.kt:301), BOOT_COMPLETED (BootReceiver.kt:33) and the 15-minute `ReconcileWorker` (Reminders.kt:133–139). The first is one-time; the second needs a reboot; the third runs in the background, where an app-targeting-31+ app cannot call `startForegroundService` — the framework throws `ForegroundServiceStartNotAllowedException` (BFSL has no WorkManager exemption), which the code catches and discards. So after a Settings force-stop, an OEM "deep clean", a crash loop, or an app update (no `ACTION_MY_PACKAGE_REPLACED` receiver), counting is off until the next reboot, with no visible symptom. Opening the app — the one moment the app *is* allowed to start an FGS — never attempts it, and granting ACTIVITY_RECOGNITION from Home only bumps `permissionEpoch` (HomeScreen.kt:63–81). This is the single highest product risk after F1 because it is silent and survivable for weeks.

**F3 — no honest status surface.** The only way counting degradation is communicated is the step-service notification: a LOW-importance channel whose NO_SENSOR variant exists (StepCounterService.kt:79–84,230–240) but which is invisible when POST_NOTIFICATIONS is denied or the user disables the channel, and which is *removed* (or never shown) in the states that matter. Home shows a permission card only for ACTIVITY_RECOGNITION (HomeScreen.kt:63–81) and never says "counting is off". Combined with F2, a user can carry a phone for a week with no steps recorded and no warning. A status line plus a repair action is cheap and turns three silent failure modes into one visible one.

## 4. GAPS

- **Platform layer has zero automated tests.** `app/src/test` contains only pure-logic tests (StepMath, CsvCodec, StepCadence, StepPipeline); no Robolectric, no instrumentation, no `androidTest` source set (app/src/test listing; app/build.gradle.kts test deps). F1/F2/F4/F6/F7 are all testable with Robolectric/service-shadow tests at low cost; none exist.
- **Runtime verification never reached a foreground service.** The AVD smoke log (EV-14, AVD-SMOKE rows) records `service_present=False`, `isForeground=False`, `fgs_type_lines=0`, no notifications, and onboarding never advanced past step 1; all runtime rows are `NOT VERIFIED — EMULATOR-ATTEMPTED`. README:105–107 ("permission grants PASS, boot receiver/WorkManager reschedule PASS") is therefore an over-read of instrumentation steps, not user-flow evidence.
- **No step/GNSS hardware test:** the API 36 `aosp_atd` image has no `TYPE_STEP_COUNTER` and no real GNSS; step-accuracy, distance and pace claims are unverified (AVD rows STEP-ACCURACY/LOCATION-ACCURACY).
- **No permission-denial / revocation matrix, no Doze/force-stop/OEM-autostart test, no app-update test, no Arabic/RTL notification check, no dark-mode launch check, no large-screen/`sw600dp` test.**
- **No release build exists** (no release APK/AAB, no release merged manifest, no signing config — EV-06/EV-20/C12): FGS behavior was never validated on the packaged release artifact, and the release-artifact gate is open.
- **No crash telemetry by design (offline/no INTERNET):** an F1 crash in the field is invisible to the team; nothing in the repo would surface it.
- **Play compliance not demonstrable from the repo:** health-FGS declaration text, data-safety form, FGS task-manager justification and screenshots are console work items with no evidence here.

## 5. UNVERIFIED / OPEN QUESTIONS

1. **F1 crash confirmation on hardware.** Docs are explicit that missing prerequisites throw `SecurityException` "after you call `startForeground()`" and may crash the app; I could not run an API 34+ device/emulator to observe the crash. The gate fix is correct regardless. [inference from docs]
2. **System sticky-restart of the location FGS.** If the process dies mid-walk, the system re-creates `WalkTrackingService` while the app is in the background; whether Android 14+'s while-in-use restriction for the `location` type applies to a system-initiated restart (i.e. whether `startForeground` throws) is **not verified**. Worth a device test; if it does throw, the walk-restore path itself crashes. [open]
3. **Coarse-only + `GPS_PROVIDER` behavior.** Android 12+ is documented to fuzz location rather than deny provider access; the exact behavior of `requestLocationUpdates(GPS_PROVIDER)` with only `ACCESS_COARSE_LOCATION` (updates vs. one-shot fuzzed fixes) was not device-tested. F6's honesty fix does not depend on the answer. [inference]
4. **Notification-permission denial behavior at API level:** assumed `NotificationManagerCompat.notify` silently drops (no `SecurityException`) so F4 is a product bug, not a crash; not device-tested. [inference]
5. **Channel-disabled case:** if the user turns off the "steps" notification channel, does the FGS notification remain visible in the Task Manager only? Behavior varies by OS version; unverified.
6. **WorkManager deferral magnitude** for the one-time reminder under Doze/app-standby is device- and OEM-dependent; no measurement. F5 wording fix is safe either way.
7. **OEM boot/autostart behavior** (MIUI, EMUI, ColorOS) for a health FGS from BOOT_COMPLETED is untested; the receiver's `QUICKBOOT` handling may be the only path on some devices and is not BFSL-exempt (F8).
8. **Predictive back** (target 36 default) with Compose Navigation 2.8.5 is expected to work through `OnBackPressedDispatcher`, but no test/scenario covers it; `enableOnBackInvokedCallback` is absent. [inference]
9. **`startForeground` with type health when the app only reads `TYPE_STEP_COUNTER`:** Play's health-FGS policy expects a health use case; whether the console declaration will accept a step counter as "health" is a policy/console question outside the repo. [open]
10. **Walk-save duplicate window:** if the process dies between `WalkRepository.save` and `deleteCheckpoint` (WalkTrackingService.kt:176–242), the next start resumes a walk that was already saved. Probability low; unverified. [code reading]
