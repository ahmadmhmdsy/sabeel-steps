## 2. VERIFIED STRENGTHS

- **Pipeline core is pure and the tested cases do hold**: reset/rebase, within-day monotonic add, same-day restart and same-day reboot do not double count (`domain/StepPipeline.kt:26-44`; `tests/domain/StepPipelineTest.kt:24-93`).
- **Write ordering is recoverable**: prefs state is written before the Room row (`data/repo/StepsRepository.kt:62-66`), so a death between them leaves the DB behind the prefs and the next reconcile repairs it — no double-count window found.
- **DataStore read-modify-write is atomic per `edit{}`** and `update()` rewrites exactly the user keys, never the sensor keys, so the two writers cannot lose each other's fields (`data/prefs/SettingsStore.kt:47-61,72-78`). Defaults match spec §1 exactly (goal 8000, 170 cm, 70 kg, unspecified, stride 0, EN, reminders off, 1140 min, onboarding false) — `SettingsStore.kt:85-97` vs `docs/product/spec.md:29-32`.
- **CSV is locale-independent in both directions**: `formatDecimal` uses `Locale.US` and parses with `toInt()/toDouble()` (JVM locale-free), so Arabic/German decimal commas cannot corrupt export or import (`data/export/CsvCodec.kt:107-123`; tested `CsvCodecTest.kt:112-124`).
- **No formula injection**: every exported cell is either an ISO date or a number produced by `row()` — no user text can start with `=`, `+`, `-`, `@` (`CsvCodec.kt:115-129`); imported dates are re-normalized through `LocalDate.parse` (`CsvCodec.kt:150-169`), so malicious cells are dropped rather than re-exported.
- **Room typing/PK is sound**: TEXT date PK, INTEGER/REAL affinity, ISO dates make lexicographic `date >= :fromDate` range queries correct (`data/db/Entities.kt:11-31`, `Daos.kt:12-19`); walks use autogen PK and `@Upsert`/REPLACE semantics are safe for single-row writes.
- **No UI-thread data access** apart from the one `runBlocking` noted in L1: all screens use `collectAsStateWithLifecycle` (`ui/screens/HomeScreen.kt:61`, `SettingsScreen.kt:75`, `HistoryScreen.kt:45`, `InsightsScreen.kt:43`), no `GlobalScope`, no `allowMainThreadQueries`.
- **Zero/negative guards exist** for goal (`HomeScreen.kt:93`, `HistoryScreen.kt:86`), distance (<50 m ⇒ pace 0, `domain/StepMath.kt:63-64`), empty lists (`StepMath.kt:42,44-45`), calories clamp ≥30 kg (`StepMath.kt:24`), and importer rejects negatives (`CsvCodec.kt:158-159`).
- **Goal notification is once-per-day guarded**, so the 1.5 s writer loop cannot spam it (`platform/Notifications.kt:127-133` called from `StepCounterService.kt:187,204`).

**High-finding detail.**

**H1** is the only finding where the app can *lose user data it was explicitly asked to restore*. The spec demands a DB-vs-pipeline max (`spec.md:55-58`), and neither `recordRawStep` nor `reconcile` ever reads today's Room row before writing (`StepsRepository.kt:66,87`). The import path (`CsvIo.kt:47-50`) writes the row and never raises the pipeline's `todaySteps`; the writer then overwrites it within 1.5 s of the next step. Fix both sides, and add a test that imports a today row into a live pipeline.

**H2** is a privacy/contract bug, not just a counter bug: the dialog promises erasure (`strings.xml:150-152`), but `deleteAll` only clears the three stores (`AppViewModels.kt:241-251`). A foreground service survives, so the first walk after "delete everything" resurrects a day row — and because the non-volatile `lastWritten*` fields are unchanged, if `settings.clearAll()` fails (it is wrapped in `runCatching`) the row can also be re-written from the stale in-memory pipeline on the next write. `walk_checkpoint.json` and `WalkTracker.state` are untouched too.

**H3** is a spec conflict, and the test at `StepPipelineTest.kt:61-69` asserts the code's choice, so "fix the test" is not an accident: it deliberately books the previous day's last steps to the new day. For a 1.5 s writer tick that is negligible; across a service outage it can book hours/days. Because the same pipeline is the only source of truth, the wrong attribution is permanent in the DB.

**H4** is two half-bugs that compose: the writer's midnight tick is legitimate (`StepCounterService.kt:176,184-186`), but `activeMinutesToday` still holds the previous day's number until `cadence.onEvent` sees the new date (`StepCadence.kt:43-52`), and `seed()` then reads the polluted row (`StepCounterService.kt:88-94`). The same class of bug hits at H1's boundary: the cadence ring is not day-aware outside the sensor callback.

## 4. GAPS

- **Test coverage is pure-Kotlin only and thin relative to claims.** 4 classes / 41 tests / ~412 lines, all JVM; no Robolectric, no `room-testing`, no `kotlinx-coroutines-test` (only `junit:junit` is declared, `app/build.gradle.kts:94-95`; grep found no other test deps). Untested: `StepsRepository` (all aggregation, midnight, reconcile, monotonicity), `SettingsStore`/`DataStore`, both DAOs/entity mappers (incl. route JSON), `CsvIo` (SAF + import merge), both services (coalescing, flush, goal notify, checkpointing), all ViewModels, `Notifications` once-per-day, `Reminders.delayUntilNext` (its docstring says "unit-testable by construction" but no test exists), and `DateKey.today(now, zone)` (only `minusDays/epochDay` are tested). Estimated exercised share of the ~1,785 scoped main-source lines: ~15 %, and **0 % of Android-bound data code**.
- **Spec §8 checkbox "date rollover, aggregation, CSV escaping" is not met for aggregation or rollover-as-aggregation**: only the pure pipeline function is tested; the repository path that actually writes rows is not.
- **No CSV format version column / no walk export / no documented merge policy** (silent replace of matching dates, not shown to the user).
- **No schema JSON, no migration tests, no CI config, no lint/static-analysis artifacts in repo**; README's "41/41 pass" and "PASS=33, FAIL=0" are unverifiable from source alone (no Gradle run here).
- **Spec §2 BMI algorithm is not implemented anywhere** (grep for BMI/height-weight computation: none; only stride uses height) — optional in spec, so a gap not a bug.
- **No instrumentation/device test for the sensor pipeline** (README only claims an emulator smoke pass); midnight/DST/reboot/two-process races have no test at any layer.
- **No data-corruption handling** for DataStore/Room (`readStepState` swallows all errors to "initial state", `Entities.kt:82-90` swallows bad route JSON to empty) — silent degradation with no diagnostic.

## 5. UNVERIFIED / OPEN QUESTIONS

- **No build/test execution**: cannot confirm "41/41 pass", APK hash, lint, or that the `@Upsert` codegen compiles; all findings are static.
- **Inference**: `runBlocking` ANR magnitude (bounded by `withTimeoutOrNull(800)`), battery cost of 3 DataStore writes/1.5 s, and actual TYPE_STEP_COUNTER event rate are estimates, not measured.
- **Inference**: WorkManager/START_STICKY recovery timing after force-stop, Doze and OEM killers — determines how often H3/M2/M6 actually fire. Device test needed (force-stop → reopen → walk; screen-off overnight).
- **Inference**: `ZoneId.systemDefault()`/DST behaviour is standard java.time, but no test crosses a DST or manual-clock boundary; the date-backwards data loss (M7) is reasoned from code, not reproduced.
- **Open**: should H3 be fixed to spec (drop the delta) or should the spec be amended to "attribute to new day"? This is a product decision the Lead should force — the test currently encodes the code.
- **Open**: is losing walks on CSV migration (M4) acceptable for v1? If import is the backup story, it needs walks.
- **Not verified in this session**: Arabic-locale rendering of exported numbers on a real AR device (code uses Locale.US, so digits are Latin; whether that is desired is a product call).
