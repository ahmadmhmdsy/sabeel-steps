The test for a safe helper is not "≥2 call sites" (the plan's gate): it is **no parameter whose value is fixed at every call site, and a third call site must not require a new parameter**. By that test two of the six should be cut: **StatCardGrid** (largest row, pure spec-growth trap; the four sites' cost is the entries, not the branch) and **shared status flows** (A10 shows it is a behaviour-contract decision, not a shrink). `SettingsRowShell` is third — keep the read at the call site or you have introduced the parameter A11 predicts. P7's helper fails the same test in the opposite direction: it is parameterised so hard that it saves almost nothing.

## 3. The oracle install

P0 asks for 30 states × 3 font scales × 2 locales = **180 images in 0.5 day**. At 80 s/image that is four hours with no setup, no triage and no re-capture; the Advocate's measured capture cost (90–150 s per cell) makes the baseline 4.5–7.5 h, re-runs after P2/P3/P4 another 13.5–22.5 h, the four-device matrix 10–16 h — roughly 4–7 unaccounted engineer-days against P0's 0.5. The states are not free: the counting state needs a running FGS; STOPPED/NO_SENSOR come from `StepSensors.availability` reading SensorManager defaults (`StepSensors.kt:19–30`), which no Settings toggle and no documented adb command changes; `NO_PERMISSION` is unreachable on API 26 (`Permissions.kt:12–13, 21–22`). P0 names no mechanism column and no empty cells, so the 3×4 matrix is already device-dependent. The oracle spec also drifts before it exists: P0 says fontScale 1.0/1.3/1.5 (`:38`), §5 says 1.0/1.4/1.5 (`:99`).

What the room creates that did not exist: a visual golden corpus and a four-device manual QA matrix, neither versioned in the repo, neither reproducible from a commit, with no owner after close and no cadence after the first release. At the next change to Home/Settings/Walk someone must re-capture a subset, adjudicate diffs and update baselines; that recurring cost is larger than the 546 lines ever save. The first "expected" diff — a Compose BOM bump, an emulator image, GPU antialiasing, a font metric — will be adjudicated by the person who made the change and re-baselined. From that moment the oracle certifies its author, and the plan's rule "any unexpected pixel move reverts" has no definition of *expected*, no independent adjudicator, no pinned image, no hashes.

A witness must be able to fail against its author's interest and be reproducible by another operator. As written, the matrix is neither deterministic nor independent; it can witness gross regressions (blank screen, missing card, wrong locale) — worth having — but not the failures this plan actually risks: dialog state after rotation (A13), the 1.35 font-scale window (A11), the midnight fallback (A12), the erase ordering (A3). The plan says "the real witnesses are the screenshot matrix and the device matrix"; that makes its C1 claim rest on an artifact that does not exist, has no owner, cannot see the audit's own findings, and cannot currently be run — `docs/legal/BLOCKERS.md:146–159` (B7) records that the repository has no device-verified run and that a counter phone still has to be measured. A manual oracle installed without ownership and determinism is a ritual; installing it as the price of a one-time refactor is the largest hidden cost in v1.

## 4. The customer's denominator

Where the attack is valid: the plan's primary metric is `app/src/main` Kotlin only (`:27`), so its 546 lines are 0.38% of the 142,456 tracked text lines the customer measured (my independent re-count at HEAD `b687f16` reproduces 350 tracked files, 73 files / ≈121,300 lines under `docs/legal/sources/`, 62 `.kt` / 10,348). The plan settles the pack's open metric decision (`evidence-pack.md:55`) by fiat and never mentions the mass; P1 is Δ0 by construction and raises the goal-setting read from 4 files to ~6 — the one readability change it makes is unmeasured. The customer's 4-file/2,246-line "goal change" measure is the right shape for what he asked.

Where it is a category error: the 85% is legal evidence snapshots (24 HTML files, 121,592 lines) — not code, not behaviour, not loaded to change a screen — and F15 has already ruled them KEPT as evidence. Moving them is a repository/legal decision outside this room's C1–C6, and it would not reduce what a developer must read to change a setting, nor make the app more extensible. Context cost is task-shaped, not tree-shaped: an agent that never needs the EULA archive never pays for it, while it pays for the 908-line settings screen repeatedly. The 0.38% is valid framing for a one-off code delta against a static archive; it is not a shrink KPI. (The customer's text-only filter also excludes 48 tracked `.png` files and the fonts, so the tree figure is a chosen filter, not the whole mass.)

The metric hierarchy, if the room wants one: **L1 code plane** — all `*.kt` under `app/src`, reported as the 5-tuple + tokens; the only plane a code shrink may claim. **L2 task plane** — for a fixed question list (change the goal default; add a settings row; resume an interrupted walk) the files, lines and tokens that must be read and changed; this is what "agent readable" means and what P1 should be judged on. **L3 repo plane** — tracked tree classified as code / app resources / docs / legal evidence / binaries; always reported, owned by the F15 decision, never a target of the shrink. Rule: never sum the planes; every claim names its plane; the room reports L1 improvement, L3 unchanged, and L2 measured — or explicitly unmeasured. If the owner wants L3 smaller, the two-hour evidence move is the correct instrument and a separate decision.

## 5. The 2x question, once more

The refutation is complete only inside three invariants: (i) the measured object is all `*.kt` under `app/src` as F2 defines it; (ii) the oracle is the 108 byte-identical tests (T1); (iii) C1 fixes every pixel and every string. Inside them: 50% needs main ≤3,852, and deleting all 5,021 ui raw lines still leaves the corpus at 5,327; 25% is 2,587 corpus lines, below the 2,671 import/comment/blank floor alone; 10% is 1,035, below the 1,322 test lines alone. T2 changes none of this (main may be ≤3,852 even with tests at 1,169).

The shapes the arithmetic misses are denominator moves, not rewrites. The Advocate steelmanned them and I confirm the numbers: a ground-up rewrite of the ui saves about 1,360 of 3,887 ui code lines (≈8,990 corpus — still short, because non-UI main alone is 4,005 > 3,852); code generation from a descriptor counts in the corpus and replaces rather than adds; a feature deletion (walk ≈ 1,460 lines) leaves 8,890. The one move that reaches the number is relocation: moving ui and service out of `app/src` leaves `app/src/main` at 2,295 and the corpus at 2,295 + 1,322 = 3,617 = **35.0%**, with every user-visible byte intact. That is not a smaller codebase; it is a smaller measured root. The one shape that does hit 50% without touching the app is the customer's: the legal archive is 85% of the tracked text and tagging it out is a two-hour move. So the answer depends on the object being halved: code 50% is impossible; tree 50% is trivial; agent-task cost is unmeasured until L2 exists. **The invariant that makes the refutation hold is the pinned corpus: the measured set is all Kotlin files under `app/src` with no relocation, generation or language change, the oracle is the 108 frozen tests, and C1 fixes behaviour — drop any one and the arithmetic is a different problem.**

Dated **2026-12-10** (room time), on branch `shrink/verify` once the accepted plan has landed (v1's P0–P8 or equivalent): (1) `git diff --exit-code app/src/test` empty and the 108/11/0/0 XML unchanged; (2) corpus ≤9,845 with the 5-tuple + tokens published and code carrying ≥90% of the delta; (3) the three riskiest screens (Home granted/STOPPED, Settings with one dialog, Walk live) reproduce **byte-identical screenshot hashes on two independent operators** on one pinned emulator image (API 34, fixed ABI, fixed font rendering) at 1.0/1.5 × en/ar, automated capture, hashes committed, and any diff adjudicated by someone other than the change's author; (4) no landed helper has a parameter whose value is identical at every call site, and no helper grew a spec type. Fail 1–2 → the shrink failed and reverts to the last green tag. Fail 3–4 → it is "arithmetically done, unwitnessed" and cannot claim C1.
