## Attack block 1 — fatal: true — 3 h buys the tree, 70 h buys 4.5 % of L1 and an unclaimed readability

**Mechanism.** v2 correctly separates L1/L2/L3, then keeps v1's work order and prices phases by hours without a rule that maps an hour to an owner-named plane. The only phase on the owner's plane is P1 (3.0 h, −121,202 L3). The middle P2–P6 costs 55.5 h and buys −462 L1; because it is UI work it also requires the new oracle (P0 matrix 3 h + the P2/P3/P4 in-phase passes 9 h + the close matrix ~3 h), so its real price is ~70 h. L2 — the plane that means "readable for an agent", the customer's own axis — is "measured at P0, reported at close, **not claimed**" (:23, :120): by the plan's own declaration the middle's readability benefit cannot be measured before the work and cannot fail it after. The §4 menu (:96–:106) offers B1–B9 but never the subset its own numbers favour: P1+P8, i.e. 8 h of phase time (≈12–13 h with the P0-lite — P0's 6 h minus its 3 h matrix — and a close-lite of ≈1.5–2 h once the final matrix is not needed), for −121,202 L3 and −34 L1.

**Evidence.**

Hours/deltas: `:48–:60`; middle 19+15+11+6+4.5 = **55.5 h** (44 h engineering-only — the "42-hour middle" shorthand understates it), Δ −462; 462/10,348 = **4.5 % of L1**, 462/142,456 = **0.32 % of L3**; program rate 496/80 = **6.2 L1 lines/h** (`:62`), tree rate 121,202/3 = **40,400 L3/h** (`:62`). Four of the five middle rows sit below the program mean and below P8's 6.8/h; P4–P6 are 21.5 h for 89 lines = **4.1 L1/h**. The oracle exists only because of the middle.

The 80 h is also under-priced by the plan's own rules. "+ 8 per-commit gate runs × 0.25 h = 2.0" (`:59`) contradicts "one commit per row" (`:136`) and "Gate (C4), after every commit" (`:113`): P2 12 + P3 4 + P4 5 + P5 3 + P6 2 + P8 4 ≈ 30 rows, plus P1 and close ≈ **32 commits** = 8 h of gates, not 2 (+6 h). The "revert/bisect buffer" is 3.0 h (`:59`), but one failed P2 row = revert + gate + one 3 h matrix pass + re-baseline/adjudication ≈ **4.4 h**, so the buffer cannot absorb the first failure of the riskiest row. The matrix is priced at 80 s/cell; the Expert measured **90–150 s per cell** (`06:55`), so five passes are **17–28 h**, not 15. The program is therefore **88–103 h** before a single row fails.

**Consequence.** Under the plan's own default — "Default if silent: **B1 + all code phases**" (`:108`) — silence spends 88–103 h to deliver −496 L1 (4.8 %) and −121,202 L3 (85.1 %). 100 % of the tree win and 0 code lines come from P1's 3 h; P8's 5 h buys 34 lines at the second-best rate without a new oracle; the 70 h middle buys 462 lines (4.5 % of L1, 0.32 % of the tree), installs the 17–28 h oracle, and its L2 effect is *unclaimed by design*. The rule the plan needs and does not state: **fund a row only if it moves a plane the owner named, or beats the program's mean rate without installing a new recurrent witness, and it passes the Expert's helper test; everything else waits until the owner names a code-size KPI.** By that rule P1 and P8 are funded today; P2 only on an explicit code mandate (best rate, worst risk, Expert-cut); P3–P6 never at 4–5 lines/h. If the customer's question is the tree, the answer is 3 h; if it is code, the answer is 5 h of P8 — the plan's 80 h is neither.

**Falsification.** Name an owner-named KPI that the 462 middle lines move more than P1's 3 h moves L3 (the middle's L3 delta is 0) or more than P8's 5 h moves L1 (34 lines), or show an L2 gate that fails the plan if task-read grows. v2 states L2 is "not claimed" and prices no L2 gate; the flaw stands.

## Attack block 2 — fatal: true — adding cells to a ritual does not make a witness

**Mechanism.** v2 converts the oracle from an imaginary 0.5-day line into a priced 136-cell, five-pass matrix (`:115`) and adds 1.35/1.4 threshold cells and rotate-with-dialog checks (`:15`, `:116`) — while keeping the structure the Expert said fails: the same engineer captures, the same sponsor adjudicates, no pinned image, no capture automation, no committed hashes, no second operator. `:115` says the cells are "diffed to the P0 baseline and adjudicated by the owner"; the owner is the product owner who ordered the refactor and whose silence defaults to the plan (`:108`), so the adjudicator is the change's sponsor. The Expert's closing condition (`06:77`) requires the opposite: byte-identical hashes on **two independent operators**, one **pinned emulator image** (API 34, fixed ABI, fixed font rendering), **automated capture**, **hashes committed**, and any diff "adjudicated by someone other than the change's author". v2 adopts none of the five; R5's tool list is tree/tokens/split/dup/sha256, with no capture or image-diff tool (`:40`). Cells answer coverage; they do not answer independence.

**Evidence.** `:115` (the sentence), `:108` (owner and default), `:126` (v2's own admission that its safe-sounding sentence is "false for three things", and that TalkBack "stays named unverified"), `:40` (R5), `06:77` (closing condition 3), `06:57` ("the first 'expected' diff … will be adjudicated by the person who made the change and re-baselined. From that moment the oracle certifies its author"; "no owner after close and no cadence after the first release"). The cells are also not producible as specified: `06:55` — the counting state needs a running FGS; STOPPED/NO_SENSOR come from `StepSensors.availability` reading SensorManager defaults (`StepSensors.kt:19–28`), "which no Settings toggle and no documented adb command changes"; NO_PERMISSION is unreachable on API 26 (`Permissions.kt:12–13, :21–22`). v2 concedes v1 "named no mechanism" (`:15`) and its §5 still names none. The 30 states are never enumerated (`:115` inherits `02-plan-v1.md:97`'s partial list: "Home 3 states × 3 fontScales × 2 locales, Walk live+summary, Insights, Settings"), so a second operator cannot even capture the same matrix without re-specifying it. The repo's only screenshot-capable device reports no step counter in every Home capture (`design-implementation/EVIDENCE.md:18–20`), the release-validation image returns blank screencaps (`README.md:135`), and B7 — no physical-device run — is open (`docs/legal/BLOCKERS.md:146–161`). Finally, the baseline is not committed: `:115` says "diffed to the P0 baseline" but no baseline images or image hashes are named as committed (R5's sha256 covers tooling, not captures), and `:33` counts non-text files "separately" without them. The matrix is not reproducible, so "byte-identical on two operators" cannot be attempted.

**Consequence.** The 15 h (17–28 h at measured cost) certifies what the sponsor already believes. After close the matrix has no owner and no cadence (`06:57`), so the first Compose BOM/font/emulator change silently re-baselines it, and R3's requirement — "a deleted line needs a named witness observed before/after" (`:38`) — is satisfied by a signature. v2's C1 claim therefore still rests on an artifact that cannot fail against the person paying for it; that is the flaw beat 1 named for v1, now priced and scaled up. It also quietly narrows: the 1.35/1.4 cells cover only Home/Insights/Walk/Settings (`:115`), while P2 changes card layout "on every screen at once" (`:125`) — the riskiest row's stated witness (`:125`) does not exist for the rest of its screens.

**Falsification.** Put in v2's own tooling/AC text: (a) a pinned image and a capture script; (b) committed baseline image hashes and a second operator producing byte-identical hashes from a fresh capture; (c) one adjudication of a real diff by someone other than the change's author or sponsor; (d) a named mechanism that produces the granted/STOPPED/NO_SENSOR cells on the capture device; (e) an enumeration of the 30 states. v2 contains none of the five, and its §5 still names no mechanism — the flaw stands.
